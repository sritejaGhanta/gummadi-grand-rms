# Build a Complete Restaurant Management System (RMS)

Act as a Senior Software Architect, Senior Full-Stack Engineer, UI/UX Designer, Database Architect, and QA Engineer with 30+ years of software development experience.

Build a complete, professional, production-quality **Restaurant Management System (RMS)** designed initially for a single restaurant with multiple floors, tables, staff members, chefs, and managers.

This must be a real, fully functional application, not just a UI prototype or static dashboard.

The system will initially operate within the restaurant's local intranet network (LAN/Wi-Fi). External internet access is not required for normal application operations.

---

Use the following technologies:

### Frontend

- TypeScript.
- Vite.

- TanStack Query for API state management.
- Axios for API communication.
- React Hook Form.

- Reusable, modular components.

### Backend
- Latest stable NestJS version.
- TypeScript.
- RESTful APIs.
- Modular architecture.
- JWT authentication.
- Role-Based Access Control (RBAC).
- Permission-Based Access Control.
- NestJS Guards, Interceptors, Pipes, Filters, and Middleware wherever appropriate.
- Swagger/OpenAPI documentation.

### Database
- PostgreSQL.
- TypeORM.
- Database migrations.
- Proper foreign keys, indexes, constraints, and relationships.
- Use transactions for order, billing, and payment operations.

### Real-time Communication
- Socket.IO / WebSockets.
- Real-time order notifications.
- Kitchen order updates.
- Service staff notifications.
- Manager notifications.

# 4. Authentication and Session Management

Every staff member must have an individual username and password.

Login is mandatory.

Requirements:

- Username/password authentication.
- Password hashing using Argon2 or bcrypt.
- JWT access token.
- Access token expiration: 24 hours.
- No refresh token system is required for the initial version.
- Logout functionality.
- Automatically redirect to login when the token expires.
- Secure token handling.
- Session tracking.
- Record login and logout timestamps.
- Record the last login time.
- Admin can deactivate accounts.
- Prevent deactivated users from accessing the application.

Since the application operates on a local intranet, keep authentication simple but do not remove essential security protections.

Never store plaintext passwords.

# 7. Service Boy / Staff Module

Staff members use the application from their mobile devices.

The staff dashboard must be mobile-first.

Workflow:

1. Staff logs in.
2. Opens the floor selection.
3. Selects the appropriate table.
4. Views the available menu.
5. Selects food items.
6. Specifies quantities.
7. Adds special instructions if needed.
8. Reviews the order.
9. Submits the order.

Once submitted:

- Order is saved in PostgreSQL.
- Kitchen receives a real-time notification.
- The order is assigned to the selected table.
- Staff can track the order status.

Staff must see:

- Available food items.
- Sold-out food items.
- Current table.
- Current orders.
- Kitchen preparation status.
- Ready-to-serve notifications.

Staff must not have access to unauthorized admin or manager functions.

## Staff Performance Dashboard

Display:

- Today's total orders received.
- Total food items ordered.
- Total food items delivered.
- Total completed orders.
- Total bills generated.
- Total tables served.
- Pending deliveries.
- Completed deliveries.

All statistics must be based on actual database records.

Chef can also:

1. Staff selects the table.

3. Manager receives a real-time notification.
4. Manager reviews the complete order.
5. Manager generates the final bill.
6. System calculates the total amount.
7. Manager prints the bill.
8. Printed bill is handed to the customer.

Billing must include:

- Restaurant name.
- Restaurant logo.
- Bill number.
- Date and time.
- Table number.
- Food item names.
- Quantities.
- Individual item prices.
- Subtotal.
- Configurable taxes.
- Discounts, if applicable.
- Grand total.
- Payment method.
- Payment status.

Support:

- Cash.
- UPI.
- Card.
- Other payment methods.

This is an initial billing system; no external payment gateway integration is required.

Implement proper bill generation and printable invoice layouts.

Prevent duplicate bill generation and duplicate payment recording.

# 22. Important Business Rules

1. A staff member cannot order a food item marked Sold Out.
2. Only authorized users can change food availability.
3. Each order must belong to a valid restaurant table.
4. Every order item must maintain its own kitchen status.
5. Every prepared food item must be associated with the responsible chef.
6. Every delivered food item must be associated with the responsible staff member.
7. A bill must contain the actual ordered items and quantities.
8. Prevent duplicate bill generation.
9. Prevent duplicate payment recording.
10. Revenue reports must be calculated using actual completed payments.
11. Role permissions must be checked on the backend.
12. Deactivated users cannot log in.
13. All important operations must be recorded in activity logs.
14. Menu availability changes must be reflected in real time.
15. Preserve historical order and bill records even when menu items are deactivated.
